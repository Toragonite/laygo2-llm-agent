# LLM 기반 커스텀 레이아웃 생성: 오픈소스 재현과 인터페이스 개선

기술 보고서 · 2026-10-01 · 저장소 https://github.com/Toragonite/laygo2-llm-agent

## 요약

한양대 한재덕 교수 연구실의 논문 *Interactive and Automatic Generation of Primitive Custom Circuit Layout Using LLMs* (arXiv:2408.07279)는 설계자가 자연어로 지시하면 LLM이 LAYGO2용 레이아웃 생성 코드를 쓰고, 설계자가 결과를 보고 수정 지시를 반복하는 흐름을 제안했다. 이 보고서는 그 흐름을 공개 도구만으로(공개판 laygo2, SKY130, Magic, netgen) 재현해 측정 가능한 baseline을 만들고, 실패를 유형별로 분석해 LLM이 쓰기 어려운 지점을 얇은 라이브러리 층 `laygo2_safe`로 고친 뒤, 같은 과제로 효과를 쟀다.

| 조건 | 통과 (8셀 × 5회) | 처음 6턴만으로 통과 | 수정 라운드 | 비용 |
|---|---|---|---|---|
| v1 재현 (원본 API, 사람 지시) | 21 / 40 | 0 / 40 | 225 | ≈ $19 |
| v2 (`laygo2_safe`, 사람 지시) | **40 / 40** | 13 / 40 | 41 | ≈ $2 |
| v3 (`laygo2_safe`, **사람 없이 도구 출력 되먹임**) | **40 / 40** | 24 / 40 | 56 | ≈ $2.4 |

핵심 발견: baseline 실패의 대부분(라벨 기준 API 오용 134건, 배선 충돌 127건, 기하 오해 85건)은 회로 지식이 아니라 도구가 LLM에게 불친절해서 생겼다. 이 셋은 라이브러리 층으로 7 / 5 / 0건으로 줄었고, 남은 실수는 넷리스트를 코드로 옮기는 단계의 누락(회로 해석, 79 → 31건)뿐이었다. 그 누락은 라이브러리가 즉시 문장으로 짚어 주므로, 사람 대신 도구 메시지를 그대로 되먹이는 것만으로도 전부 복구됐다.

## 1. 배경과 문제

레이아웃은 회로도를 공장에 보낼 도형으로 바꾸는 작업이다. LAYGO2는 DRC를 맞춰 둔 템플릿(브릭)과 정수 격자(스터드 간격) 위에 코드로 레이아웃을 조립하는 프레임워크로, 공정이 바뀌어도 코드를 재사용할 수 있다. 논문은 이 코드 작성 자체가 진입 장벽이라는 점에 주목해 LLM이 코드를 쓰게 했고, NAND부터 32 Gb/s 직렬화기까지 13개 설계가 DRC/LVS를 통과했다고 보고했다. 다만 프롬프트 로그 링크는 만료됐고, 공정·성공률·반복성·사람의 개입량은 적혀 있지 않다. 그래서 "정확한 재현"이 아니라 **논문 서술을 따른 모의 재현**으로 조건을 명시하고 측정했다.

## 2. 방법

### 2.1 검증 파이프라인 (golden path 먼저)

LLM을 붙이기 전에 사람이 쓴 generator로 끝까지 통과하는 경로를 만들었다. `flow/check_cell.py`는 generator 실행 → Magic으로 레이아웃 생성·DRC·추출 → netgen LVS를 한 번에 돌려 JSON으로 판정한다. 이 과정에서 잡은 함정 세 가지는 판정의 신뢰도를 좌우했다.

- netgen 1.5.133은 트랜지스터 폭이 틀려도, 핀 두 개가 바뀌어도 "Circuits match uniquely"를 출력한다. 요약 문구 대신 핀 표의 `**Mismatch**`와 "Property errors"를 함께 봐야 한다.
- 계층 상태에서 `drc listall count`는 via·템플릿 조각을 단독으로 검사한 에러(깨끗한 인버터에서 17개)까지 센다. 평탄화한 복사본에서 `drc(full)`로 센다.
- Magic 8.3.460은 via 배열만 가진 하위 셀을 계층 추출에서 조용히 빠뜨린다(DRC 0인데 LVS 불일치). 게이트 수준 골든은 이를 우회했다.

8개 셀(INV, TINV, NOR, NAND2, NAND3, MUX2, TSPC FF, strong-arm latch)의 golden이 모두 DRC 0 / LVS match를 통과했다. 기준 넷리스트의 트랜지스터 크기는 워크스페이스 예시(W=1.2/2.4)가 아니라 템플릿이 실제로 그리는 값(W=0.5/1.0, finger 2개)으로 맞췄다.

### 2.2 논문 흐름의 재현

논문 Fig. 2–4를 따라 컨텍스트를 6턴 대화로 구성했다: ① 넷리스트 → 트랜지스터별 dict, ② 배치 규칙·정렬 전략, ③ 설계별 규칙과 배치 코드, ④ 배선 명령, ⑤ 핀 접근과 track 전략, ⑥ 배선과 완성 스크립트. 예제 코드는 주지 않았다(논문도 코드를 공개하지 않음). 그 뒤 사람이 결과를 보고 수정 지시를 보낸다(논문의 "Describe Modification Instructions").

### 2.3 측정 프로토콜 (`docs/protocol.md`)

| 항목 | 규칙 |
|---|---|
| 수정 지시 수준 | L1 도구 출력만 / L2 진단 / L3 고칠 방향(API·규칙) / L4 좌표·열 번호·배선 계획. **baseline은 L3 이하** |
| 실패 유형 | A API 오용 / B 회로 해석 오류 / C 배선 충돌 / D 기하 오해 / E 간격 위반. 라운드마다 다중 라벨 |
| 상한 | 시도당 수정 지시 8개. 못 넘기면 실패 |
| 오염 방지 | 지시자는 golden 코드·레이아웃을 보지 않는다. 넷리스트 소자 이름은 `XM1…`로 통일해 배치 힌트를 제거 |
| 기록 | 모델, temperature, 컨텍스트·도구의 git 해시, 시도 번호, 날짜, 지시 작성자, 토큰 |

지시 작성자는 Claude(코드 에이전트의 teammate 4명)가 설계자 역할을 맡았다. 사람 설계자가 쓴 논문과 다른 조건이며, 지시자 사이의 도움 정도 차이가 결과에 섞인다는 점을 기록했다.

## 3. 재현 결과 (v1 baseline)

gpt-4o-2024-05-13, 8셀 × 5회. 처음 6턴만으로 통과한 시도는 0회였고(40회 중 34회가 코드 실행 오류), 수정 지시 후 21회 통과.

| 셀 (트랜지스터 수) | 통과 | 통과 시 평균 지시 | 논문의 프롬프트 수 (배치/배선) |
|---|---|---|---|
| INV (2) | 5/5 | 2.2 | — |
| TINV (4) | 5/5 | 2.4 | — |
| NOR (4) | 5/5 | 4.6 | 3 / 2 |
| NAND (4) | 1/5 | 7.0 | 3 / 3 |
| NAND3 (6) | 5/5 | 4.0 | — |
| MUX2 (10) | 0/5 | — | 8 / 15 |
| TSPC (7) | 0/5 | — | 3 / 11 |
| strong-arm latch (11) | 0/5 | — | 9 / 36 |

실패 라벨 합계: A 134, B 79, C 127, D 85, E 15. 반복된 실수는 네 가지였다: 함수 반환값 모양·핀 좌표 헬퍼 오용(A), 게이트와 드레인이 같은 열이라 생기는 합선과 "핀 ±1" 식으로 고른 track(C), 행이 다른 두 점을 `route()`로 이어 생기는 큰 사각형(D), 행 길이가 다른 2D 배치 리스트로 인한 numpy 오류(큰 셀 라운드 0의 6/10, 고친 뒤에도 재발).

## 4. 개선: `laygo2_safe`

### 4.1 설계 원칙

laygo2의 아키텍처(템플릿·격자·설계 DB)는 그대로 두고, 저장소 안에 얇은 층을 올렸다. 서브모듈은 수정하지 않았다.

| v1에서 반복된 실패 | 라이브러리의 대응 |
|---|---|
| 반환값 모양 오해, grid 섞어 쓰기 | 함수마다 반환 종류 하나. `pt()`의 점은 grid를 기억하고 다른 grid에 쓰면 거부 |
| 행이 다른 두 점의 `route()` → 사각형 | `wire()`가 거부. `connect()`가 L/Z 경로를 그림 |
| 같은 열 합선, 다른 net 위의 track | 층별 물리 사각형 + net의 **점유표**. 닿거나 간격(li1 0.17 / met1 0.14 µm) 미만이면 거부 |
| 게이트 사이에 다른 게이트가 끼면 li1로 못 지나감 | 직선 → 핀 사이 track → L/Z 경로 → 바깥 track → metal2 우회 순 탐색. r12에 길이 없으면 r23으로 자동 대체 |
| tie 오류·연결 누락은 LVS까지 가야 드러남 | 셀이 넷리스트를 알고 `nmos(ref=)`·`connect()`에서 즉시 거부, `check()`가 누락·분리된 net을 나열 |
| 행 길이가 다른 2D 리스트 | `place_rows(nmos_row, pmos_row)`는 길이가 달라도 됨. 만들었지만 안 놓은 소자는 거부 |

핀의 물리적 footprint는 golden 레이아웃의 CIF에서 쟀다(드레인 strip 0.24 µm, 소스 bar ±0.225 µm, 게이트 strap 0.4 µm, via pad ±0.13 µm). 검증은 두 겹이다: 가드레일 self-test 23종, 그리고 golden 8셀을 이 층으로 다시 써서(좌표·track 번호 없이) 모두 DRC 0 / LVS match.

### 4.2 측정 (v2)

같은 8셀 × 5회, gpt-4o-2024-08-06(프롬프트 캐시 지원). 처음 6턴만으로 13회 통과, 수정 후 40/40. 라벨은 A 7, B 31, C 5, D 0, E 0. 남은 B는 세 가지였다: dict에는 맞게 써 놓고 tie를 다르게 정함, 출력·내부 net을 "드레인 한 쌍"으로만 이어 병렬 소자와 팬아웃 게이트를 빠뜨림, 재배치할 때 pfet 하나를 리스트에서 빠뜨림. 셋 다 도구 메시지를 전달한 L2 지시 1개로 고쳐졌다.

## 5. 자동화: self-heal (v3)

v2에서 사람 지시 22개 중 19개가 "도구 메시지 전달"이었다. 그래서 사람을 빼고 도구 출력(실행 오류 줄, `check()` 줄, DRC 규칙·좌표, LVS 수치·불일치 줄, 추출 넷리스트)에 "고쳐서 전체 스크립트를 내라"만 붙여 최대 8라운드 되먹였다. 결과 40/40, 처음 6턴 통과 24/40(v2 측정 후 고친 라이브러리·컨텍스트 덕), 자동 라운드 56. 큰 셀(MUX2 3.4, SAL 5.2 라운드)은 사람 진단(1.0, 2.8)보다 2~3배 느리지만 모두 통과했고 사람 시간은 0이다.

되먹임에 "지난 문제 목록(열림/고침/재발)"을 덧붙인 변형은 MUX2·SAL 짝 비교 10회에서 효과가 없었다(43 → 42라운드, 1건 실패). 음성 결과로 기록했다.

## 6. 품질: 통과 너머

통과한 레이아웃 117개(golden 8, v1 21, v2 40, v3 40)의 면적과 층별 배선 길이(평탄화 CIF의 합집합 면적 ÷ 최소 폭)를 쟀다. 면적은 LLM/golden 평균 0.98(MUX2는 spacer 셀이 없어 16% 작음), li1+met1 길이는 작은 셀 ±5%. 큰 셀에서는 LLM 쪽이 metal2를 더 썼다(strong-arm latch: golden 26 µm → v2 42 → v3 61). 자동 경로 탐색이 막히면 위층으로 올라가기 때문이며, "통과"는 같아도 품질이 갈리는 지점이자 다음 개선의 비교 기준이다.

## 7. 한계와 정직한 주의

- v1 → v2는 모델(05-13 → 08-06), 라이브러리, 컨텍스트 문구가 동시에 바뀌어 기여를 분리할 수 없다. v2 → v3도 되먹임 방식 외에 라이브러리·컨텍스트가 바뀌었다. 분리하려면 같은 버전으로 대조 실험이 필요하다.
- 지시 작성자가 Claude 4명이라 도움 정도가 달랐다(v1에서 NAND 1/5 vs NOR 5/5의 일부는 이 차이). 파일럿에서는 L4 지시로 통과시킨 적이 있어 baseline에서 제외했다.
- 논문은 프롬프트를 세는 방법, 공정, 성공률을 밝히지 않았다. 숫자의 직접 비교는 조심해야 한다.
- 고속 회로(TSPC, strong-arm latch)의 golden은 논문 그림대로 새로 그렸고 모두 nf=2로 통일했다. 연결 기준이지 성능 기준이 아니며, 시뮬레이션은 하지 않았다.
- 측정 중 발견한 도구 버그(단일 핀 레일을 길이 0으로 그림)로 v2 첫 실행을 폐기하고 라이브러리를 고정해 다시 돌렸다. 측정 후 지시자들이 찾은 결함 4개는 v3 전에 고쳤다.
- 구현의 상당 부분은 Claude Code와 함께 했다. 설계 결정과 이유는 `docs/paper_notes.md`의 "우리 선택" 표에 날짜와 함께 남겼다.

## 8. 배운 것

1. **측정이 먼저다.** golden path와 가짜 통과를 잡는 판정기가 없었다면 LLM 결과가 틀린 건지 파이프라인이 틀린 건지 구분하지 못했을 것이다.
2. **실패를 분류하면 개선 지점이 보인다.** A/C/D(도구 문제)와 B(회로 해석)를 나눈 덕에 "LLM을 더 똑똑하게"가 아니라 "도구를 덜 미끄럽게"가 정답이라는 것을 숫자로 알 수 있었다.
3. **좋은 에러 메시지는 자동화의 재료다.** 라이브러리가 틀린 줄에서 이유를 문장으로 말하게 하자, 사람의 역할이 "메시지 전달"로 줄었고 그 자리를 루프가 대신할 수 있었다.
4. **음성 결과도 결과다.** 문제 이력 되먹임은 효과가 없었고, 그 사실이 다음 시도의 방향(코드 차이 보여 주기)을 정해 준다.

## 9. 다음 과제

- 배선 품질: metal2로 가기 전에 아래층을 더 끈질기게 시도하는 경로 탐색 → metal2 길이로 측정.
- 되먹임 신호: 진동하는 시도에 "직전 코드와의 차이"를 보여 주기.
- 대조 실험: 같은 라이브러리·컨텍스트로 사람 지시 조건을 재측정해 되먹임 효과를 분리.
- 게이트 수준 셀(latch, D-FF): golden은 준비됨. 논문 Fig. 5의 게이트 수준 컨텍스트와 판정기의 평탄 추출 전환이 필요.
- 상류 기여: `route()`의 정렬 검사와 입력 검증은 laygo2 본체에 이슈/PR로 낼 만하다.
